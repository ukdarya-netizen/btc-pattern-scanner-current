Задание для Replit бота: Фрактальный Паттерн-Мэтчинг и Подтверждение Объемами для BTC

1. Цель Бота

Создать автономного программного агента (бота) на платформе Replit, который будет выполнять две основные функции:

1.
Фрактальный Паттерн-Мэтчинг: Идентифицировать схожие исторические ценовые движения (фракталы) для пары BTCUSDT, накладывать их на текущий график и формировать предварительный торговый прогноз.

2.
Подтверждение Объемами и Ликвидностью: После нахождения фрактала, проводить дополнительный глубокий анализ текущей рыночной ситуации с использованием объемов, кластеров ликвидности и данных стакана для подтверждения или отклонения предварительного прогноза.

Конечная цель — генерировать высоковероятные торговые сигналы с конкретными параметрами для входа, стоп-лосса (SL) и тейк-профита (TP), ориентированные на максимальную прибыльность и предназначенные для использования в скальпинговой стратегии с высоким плечом.

2. Технические Требования и Детали Реализации

2.1. Источники Исторических Данных

Бот должен получать исторические данные по свечам (OHLCV - Open, High, Low, Close, Volume) для пары BTCUSDT. Для обеспечения надежности и полноты данных, необходимо использовать API следующих бирж:

•
Bybit API: Предпочтительный источник.

•
BingX API: В качестве резервного или дополнительного источника.

Детали реализации:

•
Использовать официальные клиентские библиотеки (если доступны) или прямые HTTP-запросы к REST API бирж.

•
Обрабатывать лимиты запросов (rate limits) API, используя задержки или экспоненциальную отсрочку (exponential backoff).

•
Хранить полученные исторические данные локально (например, в CSV-файлах или легковесной базе данных SQLite) для быстрого доступа и минимизации запросов к API. Данные должны быть организованы по таймфреймам.

•
Обеспечить регулярное обновление исторических данных (например, раз в день для 1D свечей, раз в 4 часа для 4H свечей).

2.2. Глубина Истории

Анализ исторических данных должен проводиться с 2013 года по текущий момент. Это критически важно для поиска фракталов, охватывающих несколько полных рыночных циклов (бычьи и медвежьи рынки), что повышает статистическую значимость найденных паттернов.

2.3. Таймфреймы для Поиска Фракталов

Поиск схожих ценовых движений должен осуществляться на следующих таймфреймах:

•
1-дневные (1D) свечи: Для выявления долгосрочных трендов и крупных структур.

•
4-часовые (4H) свечи: Для более детального анализа среднесрочных движений, которые могут быть актуальны для скальпинга.

Важно: Основной паттерн-мэтчинг будет происходить на этих таймфреймах. Подтверждение объемов и ликвидности (см. п. 2.5) будет использовать более мелкие таймфреймы (15M, 5M) для уточнения.

2.4. Критерии Схожести (Метрика Паттерна) для Фракталов

Для определения того, насколько два свечных движения (фрактала) "похожи", необходимо использовать комплексную метрику. Это обеспечит высокую точность и надежность паттерн-мэтчинга.

Алгоритм сравнения паттернов:

1.
Нормализация данных:

•
Для каждого паттерна (исторического и текущего) извлечь последовательности цен (Close, High, Low) и объемов.

•
Ценовые данные: Нормализовать каждую последовательность цен к диапазону [0] [1] или [-1, 1] относительно начальной цены паттерна. Например, normalized_price[i] = (price[i] - price[0]) / price[0]. Это позволит сравнивать форму движения независимо от абсолютной цены.

•
Объемы: Нормализовать объемы внутри каждого паттерна относительно среднего объема этого паттерна. Например, normalized_volume[i] = volume[i] / average_volume_in_pattern.



2.
Метрики схожести:

•
Динамическое Искажение Времени (Dynamic Time Warping, DTW): Это мощный алгоритм для измерения схожести между двумя временными рядами, которые могут отличаться по скорости или длительности. DTW будет использоваться для сравнения нормализованных ценовых последовательностей (Close, High, Low).

•
dtw_distance_close = DTW(normalized_close_current, normalized_close_historical)

•
dtw_distance_high = DTW(normalized_high_current, normalized_high_historical)

•
dtw_distance_low = DTW(normalized_low_current, normalized_low_historical)



•
Корреляция Объемов: Использовать коэффициент корреляции Пирсона для сравнения нормализованных последовательностей объемов.

•
volume_correlation = Pearson_Correlation(normalized_volume_current, normalized_volume_historical)



•
Схожесть Формы Свечей: Дополнительно можно ввести метрику, сравнивающую относительные размеры тел и теней свечей (например, (Close - Open) / (High - Low)). Это может быть включено в DTW или как отдельный фактор.



3.
Комбинированный Показатель Схожести (similarity_score):

•
Объединить результаты DTW-дистанций и корреляции объемов в единый показатель схожести. Например, similarity_score = (1 - (dtw_distance_avg / max_dtw_possible)) * weight_price + volume_correlation * weight_volume.

•
max_dtw_possible — это максимальное теоретическое значение DTW для двух паттернов данной длины.

•
Веса (weight_price, weight_volume) должны быть настроены так, чтобы сумма была равна 1. Например, weight_price = 0.7, weight_volume = 0.3.

•
Чем выше similarity_score (ближе к 1), тем сильнее схожесть.



2.5. Длина Паттерна

Длина искомого паттерна (количество свечей) должна быть в диапазоне от 30 до 100 свечей для выбранных таймфреймов (1D и 4H). Это позволяет:

•
Захватывать достаточно продолжительные и значимые рыночные структуры.

•
Избегать чрезмерной детализации, которая может привести к шуму или отсутствию статистически значимых совпадений.

•
Обеспечить достаточное количество исторических совпадений для статистического анализа.

2.6. Дополнительный Анализ Объемов и Ликвидности для Подтверждения Сигнала

После того как потенциальный фрактальный паттерн идентифицирован с высоким similarity_score, бот должен провести дополнительный глубокий анализ текущей рыночной ситуации с использованием данных реального времени (или почти реального времени) по объемам, кластерам ликвидности и стакану. Этот этап является критически важным для повышения надежности и прибыльности сигналов.

Источники данных для подтверждения:

•
Текущие свечи (OHLCV) на младших таймфреймах: 15M, 5M, 1M (через API Bybit/BingX).

•
Данные CVD (Cumulative Volume Delta): Получать из вашего текущего BTC-бота (предполагается, что он будет предоставлять API для этого) или напрямую с бирж/сервисов (например, CoinGlass).

•
Карты ликвидаций (Liquidation Heatmap): Получать из CoinGlass API (или Coinalyze API в качестве резерва).

•
Данные стакана (Order Book): Получать из API Bybit/BingX (уровни Bid/Ask, объемы).

Критерии подтверждения (после нахождения фрактала):

1.
Анализ CVD (Cumulative Volume Delta):

•
Направление: Текущий CVD на 15M и 5M таймфреймах должен подтверждать направление, предсказанное фракталом. Например, если фрактал предсказывает long, CVD должен показывать устойчивое доминирование покупателей (положительная дельта).

•
Дивергенции: Отсутствие значимых дивергенций между ценой и CVD на 15M/5M таймфреймах, которые могли бы указывать на слабость текущего движения или потенциальный разворот.

•
Сила: Значение CVD должно быть выше определенного порога, указывающего на активное участие рынка.



2.
Анализ Кластеров Ликвидности (Liquidation Heatmap):

•
SL-зона: Вблизи предполагаемого уровня Stop Loss (SL) должна находиться значительная концентрация ликвидности, которая будет выступать в качестве "магнита" или "барьера". SL должен быть размещен за этим кластером, чтобы избежать преждевременного выбивания.

•
TP-зона: Вблизи предполагаемого уровня Take Profit (TP) также должна быть концентрация ликвидности, которая может служить целью для цены. TP должен быть размещен перед этим кластером, чтобы зафиксировать прибыль до того, как цена столкнется с сопротивлением.

•
Плотность: Суммарный объем ликвидаций в кластерах SL/TP должен превышать заданный порог (например, $5-10 млн USD).



3.
Анализ Стакана (Order Book Imbalance):

•
Дисбаланс: Оценка дисбаланса в стакане (соотношение объемов бидов и асков) на ближайших 10-20 уровнях. Дисбаланс должен подтверждать направление сигнала. Например, для long сигнала, объем бидов должен быть значительно больше объема асков в пределах определенного ценового диапазона (например, 0.5% от текущей цены).

•
Крупные ордера: Поиск крупных лимитных ордеров (например, > 50 BTC) в стакане, которые могут выступать как уровни поддержки/сопротивления. Для long сигнала, крупные биды должны быть ниже текущей цены, а крупные аски — выше, но не слишком близко к TP.



4.
Объемы на Пробое/Отскоке (для текущей свечи):

•
Если фрактал предполагает пробой ключевого уровня, текущий объем на 15M/5M свече должен быть выше среднего объема за последние N свечей (например, на 20-50%).

•
Если фрактал предполагает отскок от уровня, текущий объем должен показывать признаки истощения (например, снижение объема при подходе к уровню, а затем увеличение объема при отскоке).



Комбинированный Показатель Подтверждения: Бот должен присваивать "очки" или "вес" каждому из этих факторов подтверждения. Итоговый сигнал будет считаться валидным только если суммарный показатель подтверждения превышает определенный порог.

2.7. Логика Прогноза

После успешного нахождения схожего фрактала и его подтверждения объемами/ликвидностью, бот должен формировать максимально конкретный прогноз на основе анализа последующего движения цены в исторических аналогах.

Детали реализации:

1.
Сбор исторических результатов: Для каждого найденного исторического фрактала, который имеет высокий similarity_score с текущим паттерном, необходимо проанализировать его последующее движение цены.

2.
Определение expected_price_change_pct и expected_time_horizon_days:

•
Для каждого исторического аналога определить максимальное прибыльное движение и его длительность до достижения SL/TP или до завершения движения.

•
Рассчитать среднее или медианное значение этих параметров среди всех успешных исторических совпадений.



3.
Расчет probability:

•
probability = (количество успешных исторических совпадений) / (общее количество исторических совпадений).

•
Успешным считается совпадение, которое привело к достижению TP до SL.



4.
Определение suggested_sl_pct и suggested_tp_pct:

•
На основе анализа SL и TP, которые были бы установлены в исторических аналогах и привели к прибыльным сделкам.

•
Использовать среднее или медианное значение SL/TP из успешных исторических совпадений.

•
Обеспечить минимальное соотношение Risk/Reward (RR) не менее 1.5. Если исторические данные не позволяют достичь этого RR, сигнал должен быть отклонен или скорректирован.



2.8. Формат Выходного Сигнала

Сигнал от бота должен быть представлен в формате JSON и содержать следующую информацию. Этот JSON будет отправляться через API-эндпоинт.

JSON


{
  "pattern_id": "уникальный_идентификатор_найденного_паттерна_и_времени",
  "match_date": "дата_начала_совпадения_с_текущим_графиком_в_формате_ISO8601",
  "similarity_score": 0.95, // Оценка схожести паттерна (от 0 до 1)
  "confirmation_score": 0.80, // Оценка подтверждения объемами/ликвидностью (от 0 до 1)
  "overall_signal_score": 0.85, // Общий скоринг сигнала (комбинация similarity_score и confirmation_score)
  "direction": "long", // Прогнозируемое направление: "long" или "short"
  "expected_price_change_pct": 5.0, // Ожидаемое изменение цены в процентах
  "expected_time_horizon_days": 3, // Ожидаемый временной горизонт в днях
  "probability": 0.75, // Вероятность успеха прогноза (от 0 до 1)
  "suggested_sl_pct": -2.0, // Предлагаемый SL в процентах от текущей цены
  "suggested_tp_pct": 4.0, // Предлагаемый TP в процентах от текущей цены
  "historical_matches_count": 15, // Количество исторических совпадений
  "historical_performance": [
    { "outcome": "profit", "pnl_pct": 4.5, "duration_days": 2, "sl_pct": -1.8, "tp_pct": 4.2 },
    { "outcome": "loss", "pnl_pct": -2.1, "duration_days": 1, "sl_pct": -2.0, "tp_pct": 3.5 },
    // ... (список результатов исторических аналогов с их SL/TP)
  ],
  "current_market_data_snapshot": { // Снимок текущих данных, использованных для подтверждения
    "price": 65000.00,
    "cvd_15m_delta": 0.0015, // Пример: дельта CVD за 15 минут
    "order_book_imbalance": 0.60, // Пример: 60% бидов в стакане
    "liquidation_cluster_sl_usd": 10000000, // Объем ликвидности в кластере SL
    "liquidation_cluster_tp_usd": 8000000, // Объем ликвидности в кластере TP
    "volume_spike_factor": 1.3 // Пример: текущий объем на 30% выше среднего
  }
}



2.9. Интеграция с Текущим BTC-ботом

Бот на Replit должен предоставлять простой API-эндпоинт (например, HTTP GET запрос на /signal), который будет возвращать последний сгенерированный фрактальный сигнал в формате JSON (см. п. 2.8).

Роль Replit бота:

•
Replit бот будет выступать в качестве первичного гейта для вашего текущего BTC-бота.

•
Ваш текущий BTC-бот будет периодически опрашивать этот эндпоинт (например, раз в 1-5 минут).

•
Только если Replit бот возвращает валидный сигнал (т.е., overall_signal_score выше определенного порога, direction не neutral), ваш текущий BTC-бот будет переходить к проверке своих остальных гейтов (CVD, стакан, SL/TP кластеры, которые уже реализованы в signal.ts).

•
Параметры suggested_sl_pct и suggested_tp_pct из сигнала Replit бота должны быть использованы для установки SL/TP в вашем текущем боте, переопределяя или дополняя текущую логику.

2.10. Технологический Стек (Рекомендация)

Для реализации на Replit рекомендуется использовать:

•
Язык программирования: Python.

•
Библиотеки для работы с данными: pandas, numpy.

•
Библиотеки для технического анализа: ta-lib (для индикаторов типа CVD, если не берется извне), ccxt (для работы с API бирж).

•
Библиотеки для паттерн-мэтчинга: tslearn (для DTW), scipy (для корреляции).

•
Веб-фреймворк: FastAPI или Flask для создания API-эндпоинта.

•
Планировщик задач: APScheduler для периодического обновления данных и поиска паттернов.
